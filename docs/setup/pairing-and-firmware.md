# 初期設定とペアリング不能問題

**2026-07-25 時点の記録。** 本体入手は 2026-07-24（スイッチサイエンス）。この時点の出荷時ファームウェアは **1.2.4**（2026-04-20 公開）、公式最新は **1.4.4**（2026-07-13 公開）でした。ファームもアプリも更新が速いため、**入手時期によって出荷時の版数は変わります**。

## 症状

スマートフォンアプリ「StackChan World」での初期設定が完了しませんでした。

1. 本体を起動してサーボテストを通す
2. 本体画面に 12 桁の ID が表示される
3. アプリで「Add a new StackChan」→ 近くのデバイスをスキャン
4. 本体画面と一致する ID を選ぶ ← **ここで `No devices found`**
5. デバイス名 → AI エージェント → Wi-Fi 設定（到達できない）

## 効かなかった対処

「デバイスが見つからない」という文言なので、まずスキャン周りを疑いました。以下は全て試しましたが症状は変わりませんでした。

- アプリへの Bluetooth 権限・位置情報権限の付与（OS の設定アプリ側からも確認）
- 位置情報サービスの有効化
- アプリの強制終了・再起動、スマートフォンの再起動
- 本体の再起動、ID 表示画面に戻ってからのスキャン
- Bluetooth の OFF / ON

## シリアルログで実態が判明した

USB シリアルのログを取ると、**BLE 接続は成立していました**。

```
I (111140) NimBLE: connection established; status=0
[info] [WifiConfigServer] app Connected
I (112260) NimBLE: Config data received (42 bytes): {"cmd":"handshake","data":"1784964126892"}
I (112420) NimBLE: GATT procedure initiated: notify;
I (112440) NimBLE: Config notification sent
```

- BLE 接続は成功（`status=0`）
- アプリは接続できている（`app Connected`）
- アプリはハンドシェイクを送っている
- 本体は応答も返している（`Config notification sent`）
- **その直後、アプリからは何も来ない**（切断ログすら出ない）

つまり `No devices found` は実態と違う表示で、**止まっていたのは探索ではなく「本体が返した応答の検証」**でした。

アプリ側の実装（[m5stack/StackChan](https://github.com/m5stack/StackChan) にアプリのソースも同居）を読むと、接続 30 秒・検証 20 秒のタイムアウトを持ち、失敗時のメッセージとして `Device did not return encryption data.` / `Device verification decryption failed.` が用意されていて、検証を通過してからサーバーにデバイスを登録する流れになっています。

## 原因: 出荷時ファームウェアが古かった

起動ログに版数が出ます。

```
I (690) app_init: Project name:     stack-chan
I (696) app_init: App version:      1.2.4
I (700) app_init: Compile time:     Apr 15 2026 09:18:33
```

**1.2.4** に対して作業日時点の公式最新は **1.4.4**。9 バージョン分の開きがありました。

そして構造的に詰んでいます。

- 新しいファームウェアは OTA で入る
- OTA には Wi-Fi 接続が必要
- Wi-Fi の設定にはアプリのペアリングが必要
- **そのペアリングが古いファームウェアで失敗する**

**USB からの書き込み以外に出口がありません。**

> **自分でソースからビルドしても解決しません。** ハンドシェイクトークンを返す `firmware/main/hal/utils/secret_logic/secret_logic.cpp` は公開版がスタブで、固定文字列を返すだけです。weak シンボルとして宣言され、公式ビルド時に本物の実装が差し込まれる構造です。したがってアプリの検証を通せるのは公式バイナリだけです。

## 解決

USB で公式最新（1.4.4）を書き込んだら、**一度でペアリングが通り**、AI エージェント設定 → Wi-Fi 設定 → 音声での会話まで完走しました。

手順は [公式ファームウェアを USB で書き込む](firmware-flash.md) を参照してください。

## 踏んだ罠

### OS の Bluetooth 設定からペア設定してはいけない

確認のつもりで OS 側からペアリングすると、ボンディング済みデバイスとして登録され、**アプリ側の「新しいデバイスを探す」一覧から外れます**。登録してしまった場合は削除してください。

### シリアルポートを開くと本体が再起動する

```
rst:0x15 (USB_UART_CHIP_RESET),boot:0x2b (SPI_FAST_FLASH_BOOT)
```

**ログ取得と本体操作は同時にできません。** 初期設定の途中でログを取ろうとするとウィザードがやり直しになります。逆に起動ログを頭から取りたいときは、ポートを開いたままリセットを掛ければ取れます。

### インタラクティブなシリアルコンソールは無い

`help` などを送っても応答はなく、書き込み自体がブロックします。シリアルは読み取り専用として扱うのが正解です。

### 2 つの USB-C ポートに同時給電しない

CoreS3 側から入れた 5V は M-BUS の `BUS_5V` を通ってベース側へ回るため、**両方に電源を挿すと同一レールで 2 つの電源がぶつかります**。公式ドキュメントの「双方から給電を試す」は片方ずつという意味です。給電と書き込みはかかと側のポートが推奨されています。

### サーボのゼロ点はフラッシュ全書き換えでも消えない

書き込み前後で同じゼロ点が読み出されました（`[ScsServo] id: 1 get zero pos: 460 from settings`）。**この値はサーボ本体側に保持されている**ようです。

### 本体だけで Wi-Fi を設定する画面は無い

セットアップ画面の実装（`firmware/main/apps/app_setup/workers/connectivity.cpp`）はアプリのインストールを促す QR コードを表示するだけで、アプリを迂回する導線は用意されていません。

## 充電についての注意

ファームウェアは起動時に AXP2101（電源管理 IC）の充電電流を **700mA** に設定します。

```cpp
auto ret = setChargerConstantCurr(XPOWERS_AXP2101_CHG_CUR_700MA);
```

ESP32-S3 は USB 2.0 デバイスとして動作するため、**PC の USB ポートから取れるのは 500mA が上限**です。本体の消費（液晶・カメラ・サーボ・無線）と合わせると入力上限を超えるので、**PC 給電では充電が始まりません**。給電には 5V で余裕のある USB 充電器を使ってください。

サーボが現在位置を返さない場合（`[ScsServo] ignore invalid current pos: -1`）も、電力不足のサインとして読めます。

## 教訓

**表示されるエラー文言を信じすぎず、ログを取る。** 権限を何度も見直した時間は、シリアルログを 1 回取れば不要だったものです。
